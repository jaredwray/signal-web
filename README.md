# signal-web

A feasibility spike that asks one question with evidence: **can a statically hosted web page
run a Signal client entirely in a normal browser (Rust → WebAssembly), link to an existing
account by QR code, and talk directly to Signal's servers, with no backend of ours?**

**Outcome: `BLOCKED_UNDER_CURRENT_CONSTRAINTS`.** Signal's current cryptography runs correctly
in browser WebAssembly, in every browser tested. But every Signal service host presents a TLS
certificate from Signal's own private root CA. No browser root program includes that CA, and
web pages cannot add trust anchors. As a result, no current browser can open the connections
that linking, messaging, or attachments need. Evidence, scope, and alternatives are in
[VALIDATION_REPORT.md](VALIDATION_REPORT.md).

> Unofficial experiment, not affiliated with or endorsed by Signal. It is not a messenger.
> Do not use it with a personal account or for sensitive conversations.

## Layout

| Path | What it is |
|---|---|
| `crates/signal-web-core/` | Rust → `wasm32-unknown-unknown`: libsignal-protocol (pinned), provisioning (QR linking) crypto/framing, local self-tests |
| `crates/upstream-protocol-tests/` | Runs libsignal's own `rust/protocol/tests` inside browsers (tests generated by `scripts/prepare-upstream-tests.sh`) |
| `web/` | The static site: app (`index.html`), self-test, network probe, storage test, encrypted vault (`lib/vault.js`) |
| `tools/` | Static file server (GET only, no proxy), browser drivers, test runners, evidence tools |
| `evidence/` | Sanitized results: `local/` (no network), `live/` (contacts Signal, no account), `ci/` (clean-network CI runs) |
| `docs/OPERATOR_GUIDE.md` | Reproducing the browser results yourself, and what a phone operator would do |
| `third_party/` | One vendored test-only crate with a one-line feature change (see its README) |

## Build

Prerequisites: [rustup](https://rustup.rs) (the pinned toolchain in `rust-toolchain.toml`
installs itself), `protoc` (needed by libsignal's SPQR build script), Node.js ≥ 20, and:

```sh
cargo install wasm-bindgen-cli --version 0.2.129 --locked
npm ci
npm run build:wasm          # -> web/pkg/ (not committed)
```

## Tests

| Command | Class | Needs |
|---|---|---|
| `npm test` | LOCAL | Chromium. Runs the WASM crypto + provisioning self-test and encrypted persistence across a real browser restart. Add `--browser` specs, e.g. `node tools/run-local-tests.mjs --browser pw:firefox` |
| `bash scripts/prepare-upstream-tests.sh && node tools/run-upstream-tests.mjs --include-ignored` | LOCAL | libsignal's 55 protocol tests, in a browser |
| `SIGNAL_WEB_LIVE=1 npm run probe:live` | LIVE, no account | Contacts Signal's public hosts once per target from a browser page |
| `SIGNAL_WEB_LIVE=1 python3 tools/tls_trust_evidence.py` | LIVE, no account, **not browser evidence** | openssl + public CT/CCADB data |

No test needs, or can currently use, a Signal account. The linking, messaging, and attachment
gates are blocked before an account is involved; see the report.

Browser specs (`tools/browsers.mjs`): `pw:chromium`, `pw:firefox`, `pw:webkit`,
`pw-channel:chrome`, `pw-channel:msedge`, and real browsers over W3C WebDriver such as
`wd:firefox@http://127.0.0.1:4444` (geckodriver) or `wd:safari@http://127.0.0.1:4445`
(safaridriver). CI (`.github/workflows/`) runs all of them, including Safari on macOS.

## Run the app

```sh
npm run serve               # http://localhost:8080/ : static files only
```

`index.html` tries the real linking flow and shows the browser-observable result. It shows a
QR code only after Signal's server assigns a provisioning address.
